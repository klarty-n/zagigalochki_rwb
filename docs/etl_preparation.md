# Подготовка загрузки raw → core

Рабочий материал участника 2 о подготовительном этапе профилирования.
После его выполнения получен контракт `docs/core_model.md` и реализована
загрузка; актуальный запуск и результаты описаны в `docs/load_core.md`.
Описанный ниже профилировщик сам не создаёт модель и не меняет PostgreSQL.
Существующие скрипты скачивания и загрузки `raw` не изменены.

## Запуск проверки

Из корня проекта, Python 3.10 или новее, без установки пакетов:

```powershell
python scripts/profile_source.py
python scripts/test_profile_source.py
```

Результат: `reports/raw_profile.json`. Он локальный и исключён из Git через
`reports/.gitignore`. Содержит количество записей, SHA-256 файлов, пропуски,
проверки форматов, кандидаты ключей, связи и несколько примеров проблем.
Повторный запуск обновляет отчёт. Время создания отчёта меняется.

Расширенный аудит дат, статусов, денежных сумм и других наблюдений:

```powershell
python scripts/audit_source.py
python scripts/render_audit_report.py
python scripts/test_audit_source.py
```

Основной отчёт для человека: `reports/audit_report.md`, на русском языке,
с количеством наблюдений, объяснениями и конкретными примерами.
Технические копии: `reports/audit_summary.json` и полный журнал совпадений
`reports/audit_observations.jsonl`. Ситуации могут пересекаться, их количества
нельзя складывать как число отклонённых записей.
Подтверждённые пользователем правила ведём в `docs/data_quality_decisions.md`.
Расширенный аудит ничего не отклоняет и не исправляет.

Параметры:

```powershell
python scripts/profile_source.py --data-dir data --output reports/raw_profile.json --batch-size 5000
```

Список файлов и колонок берётся из `MAPPING` существующего `load_raw.py`
без импорта или выполнения этого загрузчика. CSV читаются потоково.
Межстрочные проверки используют временную SQLite-базу на диске, которая
закрывается и удаляется после работы. Размер вставки ограничивает `batch-size`.
Для временной базы нужно свободное место на диске; её размер зависит от данных
и индексов. Скорость и потребление ресурсов на больших объёмах ещё не измерены.

## Что установлено на скачанной выгрузке

Первый полный запуск: 8 файлов, 550 759 записей, количество по таблицам совпало
с раздаточным материалом. Полных повторов строк в этих файлах не обнаружено.

| Наблюдение | Следствие для загрузки |
| --- | --- |
| `orders.order_id` уникален и заполнен | Кандидат ключа заказа |
| Пара `order_id + order_item_id` уникальна и заполнена | Кандидат ключа позиции |
| Пара `order_id + payment_sequential` уникальна и заполнена | Кандидат ключа части оплаты |
| У `review_id` 789 повторяющихся групп, 814 строк сверх первой | Нельзя объявить его единственным ключом отзыва |
| Пара `review_id + order_id` уникальна и заполнена | Кандидат ключа записи отзыва, согласовать с архитектором |
| 160 заказов без даты подтверждения оплаты | Нужна допускающая NULL колонка и проверка по статусу |
| 1 783 заказа без даты передачи перевозчику | Отсутствие даты не заменяем датой оформления |
| 2 965 заказов без даты вручения | Сохраняем NULL, не придумываем дату |
| У 610 товаров пустая категория | Товар сохраняем, правило категории согласуем |
| У 13 товаров заполненная категория отсутствует в переводах | Исходное название сохраняем, перевод может быть NULL |
| 1 278 заказов содержат товары нескольких продавцов | Связь с продавцом должна идти через позиции |
| 99 441 профиль покупателя соответствует 96 096 значениям `customer_unique_id` | Профиль и человек имеют разную гранулярность |

Проверенные ссылки заказов на покупателей, позиций на заказы/товары/продавцов,
платежей и отзывов на заказы не имеют отсутствующих непустых ключей.
Исключение среди проверенных связей: справочник переводов категорий, описанный выше.

В проверенных непустых полях дат, целых чисел и денег ошибок формата не найдено.
Это не доказывает корректность всей бизнес-хронологии или равенство денежных сумм.
Пробелы и переводы строк по краям текстов отзывов учитываются как наблюдения,
а не как основание отклонять отзыв. Массовый TRIM свободного текста не согласован.

Проверка уникальности относится к текущему снимку, а не является гарантией
для всех будущих источников. Проверка заголовков и форматов при следующей
поставке должна выполняться заново.

## Контракт будущей загрузки

Предлагаемый процесс: регистрация запуска, подготовка данных, валидация,
сравнение по ключам и содержимому, публикация изменений, журнал результата.
Ниже исходные предложения этапа подготовки; фактически реализованное
поведение и остающиеся ограничения описаны в `docs/load_core.md`.

1. `raw` читаем без изменения структуры или данных.
2. Первый запуск наполняет `core`, повторный не создаёт дубликаты.
3. Новые версии существующих сущностей обновляем только по согласованным правилам.
4. `_loaded_at` не включаем в сравнение бизнес-содержимого и не используем
   как дату изменения сущности в источнике.
5. Пустая необязательная дата становится NULL. Ошибочное непустое значение
   сохраняем с причиной в диагностике. Критические ошибки блокируют публикацию.
6. Для конфликтующих строк одного ключа не выбираем произвольную «последнюю»:
   без версии источника такой порядок не определён.
7. Отсутствие строки в следующем файле не означает автоматически удаление.
8. Фиксируем число прочитанных, принятых, отклонённых, добавленных,
   изменённых и неизменившихся записей. Для отклонений считаем именно записи,
   поскольку одна запись может нарушить несколько правил.
9. Публикация должна сохранять согласованность связанных таблиц. Ограниченные
   партии при подготовке не означают независимую публикацию половины заказа.
10. Запись о неуспешном запуске должна переживать откат бизнес-транзакции.

## Ограничение источника и большие объёмы

Текущий `load_raw.py` полностью заменяет `raw`, а у сущностей нет `updated_at`
или версии источника. Поэтому сейчас возможно сравнение полных снимков:
оно уменьшает объём обновлений `core`, но по-прежнему требует чтения снимка.
Настоящее получение только изменений потребует отдельного контракта источника
(журнал изменений, версии или надёжная дата обновления).

Профилировщик проверяет стабильность каждого файла во время чтения по размеру
и времени изменения. Он не доказывает, что восемь файлов относятся к одному
моменту источника. Для рабочей загрузки нужен завершённый набор файлов с
манифестом партии либо согласованный снимок базы. Нельзя одновременно
перезагружать `raw` и читать его без согласованного механизма изоляции.

Нагрузочные испытания, ограничения ресурсов, SLA, резервное копирование и
мониторинг ещё не реализованы. Текущий результат — подготовка к загрузке,
его нельзя считать доказательством готовности к промышленной нагрузке.

## Что получить от участника 1

- DDL `core`, ключи и порядок зависимостей.
- Соответствие исходных и целевых полей, допустимые NULL и точность чисел.
- Правила для отзывов, профилей покупателей и категорий без перевода.
- Какие изменения хранят текущее состояние, а какие требуют истории.
- Согласованное размещение служебных объектов загрузки и диагностики.

После этого участник 2 реализует загрузку, а участник 3 независимо проверяет
ответы и денежные суммы по `core`. Профилирование CSV не заменяет эти проверки.
