# Загрузка raw → core: запуск и защита

Реализовано для контракта `docs/core_model.md` из ветки `feature/core-model`,
коммит `4bc3b28`. Коммиты новых файлов и push выполняет участник команды вручную.

## Быстрый запуск

В текущей локальной базе `raw` и `core` уже заполнены, повторный запуск проверен:

```powershell
python scripts/load_core.py
```

Из чистого окружения после скачивания CSV:

```powershell
docker compose up -d postgres
python scripts/load_raw.py
python scripts/load_core.py
```

Дождаться готовности PostgreSQL перед загрузкой. Нужны Python 3.10+ и
`psycopg2-binary`, как у штатного загрузчика raw. PostgreSQL — версии 16+.
Подключение по умолчанию: локальная учебная база из README.
Для другого подключения использовать `DATABASE_URL` либо `--dsn`.
Не добавлять реальные пароли в Git; параметр `--dsn` может сохраняться в истории оболочки.

Загрузку выполнять через Python-команду: SQL использует `run_id` и границу
публикации, которыми управляет этот запуск. Это не автономный psql-скрипт.
После изменения соответствия полей выполнить `python scripts/build_core_load.py`,
проверить обновлённый SQL и повторить проверку загрузки.

## Как работает

1. Запуск получает блокировку от второго такого же загрузчика и регистрирует `run_id`.
2. Для raw берутся SHARE-блокировки на время обработки: параллельная перезагрузка
   исходника ждёт, а читающие запросы остаются возможны. Цикла по строкам в Python нет.
3. PostgreSQL создаёт временные типизированные таблицы, проверяет обязательность,
   корректность преобразований, ключи и ссылки на принятые родительские записи.
4. Структурно невалидные строки сохраняются целиком с ключом и массивом причин
   в `etl.rejected_rows`. Все строки конфликтующей группы ключа отклоняются:
   произвольную «последнюю» не выбираем. Ошибки родителя документируются и у детей.
5. Новые строки добавляются, изменившиеся обновляются через `ON CONFLICT`.
   Неизменившиеся строки не переписываются. Данные, отсутствующие в следующем
   снимке, автоматически не удаляются. При отклонении новой версии старая
   опубликованная версия остаётся; это надо учитывать при интерпретации core.
6. Изменения всех бизнес-таблиц публикуются одной транзакцией. Для публикации
   берутся блокировки от конкурентной записи в core. При её ошибке изменения
   откатываются, подготовленная диагностика сохраняется, запуск получает статус failed.
7. Результат записывается в Markdown с количеством принятых/отклонённых,
   добавленных/обновлённых/неизменившихся записей.

Есть строгий режим, который запрещает публикацию при любом отклонении:

```powershell
python scripts/load_core.py --fail-on-reject
```

По умолчанию валидные записи публикуются, невалидные документируются и не
публикуются — по решению пользователя после консультации с экспертами.
Это отличается от исходного предложения архитектора о полной остановке
на любой невалидной строке; строгий режим сохраняет возможность такого поведения.

## Правила, которые уже применяются

- Пустая категория: товар остаётся, category_name = NULL.
- Нет перевода: исходный код категории остаётся, перевод = NULL.
- Пробельные поля становятся NULL, обязательные пустые поля отклоняются.
- Непустые неверные числа/даты, переполнение целевого типа и лишняя точность
  денег отклоняются с причиной; незаметного округления нет.
- Для обещанной даты принимается полночь исходного timestamp. Если придёт
  значимое время, запись будет диагностирована, а не молча обрезана до даты.
- review_creation_date переносится в timestamp с сохранением времени.
- Нулевые значения, спорная хронология, отсутствие необязательных дат и
  денежные расхождения пока сохраняются по контракту. Новые правила их
  отклонения нельзя вводить без согласования: это изменит состав core и суммы.

Наличие нуля отклонённых в текущем запуске означает отсутствие ошибок
именно этих структурных правил, а не отсутствие любых проблем качества.

## Что проверено на этой машине

- Полная загрузка настоящих 550 759 строк raw; 8 таблиц core.
- Справочник categories содержит 73 кода, включая 2 без перевода.
- Повторный запуск: 0 новых и 0 обновлённых строк, все принятые неизменны.
- 23 проверки: сохранение количества строк, трёх денежных сумм, времён отзывов,
  категорий и контрольных показателей пяти вопросов.
- В отдельной временной PostgreSQL-базе: первая загрузка, повтор, изменение
  статуса существующего заказа, неверное число, отсутствующий родитель,
  повтор ключа, сохранение старой валидной версии и атомарная остановка
  в строгом режиме с сохранением диагностики. Рабочая база в этих тестах не менялась.

Проверки выполнялись до изменения данных аналитиком и относятся к этому
снимку. Подгонять значения под контроль после введения новых правил нельзя.

## Что честно сказать о масштабировании

Преобразования выполняются наборами строк на сервере, факты разделены,
лишние обновления исключены, предусмотрены индексы, журнал и диагностика.
Но источник пока даёт полный снимок: он целиком читается при каждом запуске,
временные таблицы и блокировки требуют ресурсов. Это не CDC и не доказанная
готовность к миллиардам строк. Следующие шаги после защиты: контракт партий
и версий источника, измерение нагрузки, квоты/тайм-ауты, политика хранения
диагностики, мониторинг, резервное копирование, история и схема миграций DDL.
CREATE TABLE IF NOT EXISTS не обновляет несовместимую существующую схему.
