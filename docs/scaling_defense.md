## Сейчас и при росте

Сейчас PostgreSQL, API и дашборд работают на одном компьютере. `raw` сохраняет источник, `core` — проверенные факты и исторические снимки. Большинство объектов `mart` — SQL-представления поверх `core`. Для категорий добавлена **сохранённая** витрина `mart.category_sales_cached`: месяц × штат покупателя × категория, число единиц и сумма `price`. Категорийный отчёт API читает её; остальные показатели пока читаются из обычных представлений.

При росте планируем вынести аналитическую БД на другую машину: после успешной загрузки передавать в неё нужные проверенные данные `core`, строить там `mart`, а API направлять к аналитической БД. Стрелка `core` на рисунке означает передачу проверенных фактов; стрелка `mart` — ответ с агрегатами для API. Это **проектная схема**, второй сервер сейчас не развёрнут. Способ переноса и его задержку следует проверить отдельно до переключения пользователей.

Практический порядок: (1) поднять вторую PostgreSQL с отдельными учётными данными и резервным копированием; (2) сделать согласованный снимок нужных `core`-таблиц и перенести его на вторую машину; (3) построить там `mart`, обновить сохранённый агрегат и сравнить контрольные суммы с основной БД; (4) только после проверки направить отчётные запросы API на вторую БД; (5) настроить повторяемую передачу после каждого успешного запуска загрузчика, мониторинг задержки и проверку отказов. Для начала подойдёт пакетная передача после загрузки; если нужна частая свежесть, отдельно проектируем потоковую передачу изменений. Просто запуск второго PostgreSQL данные не синхронизирует.

Нынешний API использует один `DATABASE_URL` и для обзора, и для экранов заказов/качества. Поэтому перед переносом нужно либо передавать на аналитическую машину все `core`-таблицы, которые читают эти экраны, либо добавить в API отдельные подключения к основной и аналитической БД. Это ещё не реализовано. «Основная БД, аналитическая БД, API» на схеме — три роли; сначала API может жить на одной из двух машин, отдельную третью машину добавляют при собственной нагрузке на приложение.

## Честный замер категорий

Измерение выполнено 28.10.2026 на локальном PostgreSQL 16 с текущим учебным набором. Скрипт: `cd web && npm run benchmark:categories` (или `node server/benchmark-category.mjs`). Полный результат с датой, версией PostgreSQL, всеми запусками и размерами сохраняется в [JSON-отчёт](../reports/scaling/category_benchmark.json); прежний запуск и проверки собраны в [журнале](../reports/scaling/measurements.md). Оба запроса группируют доставленные товарные позиции по исторической категории, суммируют цену без доставки и считают единицы. Полные результаты сравнены программно: **одинаковые 74 категории, суммы и единицы**. Для каждого запроса был один прогрев и семь чередующихся запусков `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`.

| Вариант | Медиана времени выполнения SQL |
|---|---:|
| Агрегация из `core` | 97,691 мс |
| Сохранённая витрина | 2,647 мс |

`core.order_items` с индексами занимает 29 МБ, сохранённая витрина с индексом — 1576 КБ. После прогрева 10 соединений дополнительно выполнено 30 запросов к витрине пачками по 10 одновременно: 95-й процентиль времени ответа клиента — **9,970 мс**. Это локальный замер маленького набора и только SQL-запроса категорий: браузер, весь API и сеть не измерялись. Он не доказывает такую же скорость всего дашборда, загрузки или будущего сервера. Результат зависит от машины, кэша, числа пользователей и размера данных; при изменении условий замер повторяется.

## Правило свежести

`scripts/load_core.py` вызывает обновление сохранённой витрины **после успешной публикации `core`**. Обновление данных и `last_success_at` происходят в одной транзакции. При ошибке старая корректная витрина остаётся доступной, в `mart.refresh_state.last_error` сохраняется причина, дашборд показывает предупреждение и время последнего успешного обновления категорий. Остальные живые показатели могут быть свежее категорий, поэтому время в интерфейсе подписано именно для категорий. Ручное повторение: `python scripts/refresh_category_mart.py`.

Проверка сбоя: `--simulate-failure` завершился с кодом 1; после него сохранились 11 672 строки витрины, ненулевое время предыдущего успешного обновления и предупреждение. После обычного успешного обновления предупреждение очищается.

Текущее обновление использует обычный `REFRESH MATERIALIZED VIEW`: во время его выполнения чтение этой витрины может ждать завершения операции. Проверка сбоя доказывает сохранение предыдущих данных **после отката**, но не нулевое время простоя во время обновления. Для более высокой доступности понадобится отдельно проверить конкурентное обновление и его требования к индексу.

## Когда нужна вторая машина

Наша измеримая цель для категорий: **p95 не более 1 секунды при 10 одновременных запросах**. Цель для полного цикла загрузки `core` и обновления категорийной витрины: **не более 5 минут** на ожидаемом дневном объёме. Повторная локальная загрузка текущего набора 28.10.2026 прошла за **38,16 секунды** от старта загрузки до метки успешного обновления витрины (отчёт `reports/scaling/load_e94b5851-a342-4017-a718-67f87b327a0f.md`, 0 отклонённых строк). Это проверка цели на текущем объёме, а не прогноз на увеличенный.

Проверяем цели на данных ожидаемого размера, с типичными фильтрами и на планируемом железе. Сначала настраиваем индексы, исправляем тяжёлые запросы и ограничиваем число соединений. Если после этого любая цель нарушается в **трёх последовательных замерах** при ожидаемой нагрузке, выносим аналитику на отдельную машину и повторяем те же тесты. Никакого «предела PostgreSQL по числу строк» не заявляем.

## Резервная копия и восстановление

`deploy/backup.sh` создаёт архив `pg_dump` и проверяет его каталог. `deploy/test_restore.sh` восстанавливает архив в отдельную временную базу, запускает `checks/mart.sql` и удаляет тестовую базу. На локальной базе проведён фактический тест: дамп вынесен из контейнера, скопирован назад, восстановлен в отдельную базу. Сверка основной и восстановленной баз: 99 441 заказ, 112 650 позиций, 11 672 строк сохранённой витрины, сумма категорий 13 221 498,11 BRL; `checks/mart.sql` прошёл. Дамп лежит локально в игнорируемом `deploy/backups/`; внешнее защищённое хранилище и регулярное расписание ещё нужно настроить при реальном развёртывании. Реплика не заменяет резервную копию, потому что ошибочные изменения могут попасть и на неё.
