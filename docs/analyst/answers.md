## 1. Выручка и число заказов по месяцам

Бизнес-вопрос: как меняются число доставленных заказов и стоимость товаров по месяцу оформления. Период [2016-09-01,2018-09-01), валюта BRL. Только delivered. Выручка=sum(price), доставка исключена. Число заказов тоже delivered: это явно выбранное правило архитектора; сама контрольная сумма не устанавливает единственно возможный фильтр для счётчика.

Алгоритм: календарь 24 месяцев → позиции доставленных заказов → сумма до заказа → сумма и количество до месяца → LEFT JOIN календаря. Для связи заказа с позициями используется INNER JOIN, поэтому проверяется отсутствие delivered-заказов без позиций. Перемножения с платежами или отзывами нет. COALESCE создаёт ноль для отсутствующего месячного агрегата, но не заменяет неизвестную цену нулём.

Получено:24 строки; ноябрь 2016 — 0 заказов и 0 выручки; суммарно 96478 заказов и 13221498.11 BRL. Итог отдельно сверён запросом raw с EXISTS.

Бизнес-действие: при падении выручки отдельно изучать объём заказов и среднюю товарную сумму, затем категории/продавцов. Причину из одного графика не доказывать. Это месяц покупки со статусом из среза, не бухгалтерский месяц признания выручки.

## 2. Топ-10 продавцов по выручке

Вся выгрузка, delivered, выручка продавца=sum(price) только его позиций. Доставку не включаем. Заказы=count distinct order_id внутри продавца; единицы=count строк order_items. Город и штат — из справочника sellers; PK гарантирует одно совпадение. LIMIT 10 применяется после полной агрегации и сортировки. Если понадобится фильтр штата, применять его до выбора топа.

Лидер:4869f7a5dfa277a7dca6462dcf3b52b2, город guariba, штат SP; 1124 заказов, 1148 единиц, 226987.93 BRL.

Бизнес-действие: оценить концентрацию продаж и приоритет сопровождения продавцов. Числа заказов разных продавцов нельзя складывать в общее количество: один заказ может содержать нескольких продавцов. Число единиц источника не доказывает частичный фактический выкуп, которого в данных нет.

## 3. Средний чек и состав заказа

Вся выгрузка, delivered. На первом шаге одна строка на заказ: order_value=sum(price+freight_value), item_lines=count distinct(product_id,seller_id), units=count(*) исходных физических единиц. Затем среднее этих величин между заказами. Цена и доставка уже относятся к отдельной единице в core, на порядковый номер или рассрочку их не умножаем.

Получено: чек 159.88 BRL; товарных строк 1.038537; единиц 1.142198 на заказ.

Определение «товарной строки» взято из нового контракта архитектора: одинаковый товар одного продавца в заказе — одна строка отчёта, даже если куплено несколько единиц. Это нужно озвучить преподавателю, поскольку отдельного контроля для этого среднего в задании нет. Если имеется в виду именно строка хранения, её среднее равно 1.142198; альтернативу выводит checks/block_a_diagnostics.sql. Ранее в ранних черновиках использовалась именно строка хранения; эти черновики больше не актуальны.

Бизнес-действие: различать более дорогие заказы и заказы с большим количеством единиц. Средний чек включает доставку и не равен выручке из Q1, поделённой на число заказов. Усреднять готовые месячные средние без весов нельзя.

## 4. Покупатели и повторные покупки

Вся выгрузка, все статусы: считаем повторные оформления. orders.customer_id связываем с customers.customer_id, затем группируем по устойчивому customer_unique_id человека. Повторный — минимум 2 разных order_id. Доля=100×повторные/все; округление в конце; NULLIF защищает от деления на 0 при пустой выборке.

Получено:96096 человек; 2997 повторных; 3.12%.

Бизнес-действие: начальная характеристика возврата клиентов за новым оформлением. Это не показатель повторно доставленных покупок и не когортное удержание. Разные покупатели наблюдаются разное время, поздние повторные заказы за пределами выгрузки неизвестны. Уникальных покупателей по месяцам нельзя складывать в общий итог.

## 5. Выручка по категориям

Вся выгрузка, delivered, sum(price) без доставки. Группируем по исходному products.category_name, включая NULL. Затем LEFT JOIN справочника categories для подписи: английский перевод → исходный код → «Не указана». Так две категории без перевода не исчезают, а пропущенная категория не теряет деньги. При одинаковом переводе разные исходные коды не сливаются.

Доля=100×выручка категории/сумма всех категорий; SUM(revenue) OVER() получает полный знаменатель после группировки. Округление долей до 6 знаков только при выводе, поэтому сумма отображённых долей может слегка отличаться от 100; исходные суммы сходятся точно.

Получено:74 категории; лидер health_beauty — 1233131.72 BRL; общая сумма 13221498.11 BRL. Группа «Не указана» включена.

Бизнес-действие: оценивать структуру и концентрацию товарных продаж. Доля зависит от текущего фильтра, нельзя складывать проценты по разным периодам. INNER JOIN с товарами допустим только после проверки ссылок — отсутствие карточки не должно маскироваться обычной неизвестной категорией.

## Как повторить проверку

1. core уже загружен через scripts/load_core.py с --fail-on-reject. Локальный отчёт: reports/local/load_0985938f-713c-4430-9861-b5ee2002fe25.md. Повторная загрузка для обычного SELECT не нужна. Не запускать reset и не менять raw.
2. Выполнить `python3 checks/run_block_a.py` из корня. По умолчанию используется Docker-сервис postgres. Для локального клиента: `DATABASE_URL=postgresql://hack:hack@localhost:5433/marketplace python3 checks/run_block_a.py --local-psql`.
3. Инструмент проверит наличие полей, ключи, связи, сохранение строк/сумм, выполнит пять неизменённых SQL на настоящем core и обновит CSV.
4. Убедиться в results/block_a/verification.json: status=passed, validation_scope=team_core, core_queries_verified=true и ready_for_submission=true. В текущем прогоне все указанные флаги подтверждены. При новых изменениях проверку нужно повторить.
5. При несовпадении имён/типов менять запросы только по обновлённому контракту архитектора. При потере строк/сумм передать инженеру диагностику, не исправлять raw под ответ.

Текущий подтверждённый прогон: `python3 checks/run_block_a.py`, режим team_core. Все 46 проверок прошли, CSV обновлены непосредственно из core. Первоначальная проверка источника через --source-reference была подготовительным этапом и больше не является источником актуальных CSV. Детали, время, версия сервера и хэши запросов/результатов — в verification.json. Контрольные константы находятся в проверках, не в SELECT результатов.
