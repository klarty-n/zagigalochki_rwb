# Обязательная доработка модели: вброс

Владелец: архитектор + инженер загрузки. Это контракт для согласования, НЕ уже применённая миграция. Аналитик не менял model/01_schema.sql и model/02_load.sql. Блок Б работает на текущем core; после миграции повторить все десять ответов.

## 1. Категория товара на момент продажи

Предлагаемый минимальный интерфейс:

- core.order_item_categories: order_id + order_item_id (PK и FK к позиции), category_name (nullable FK), provenance / captured_at. Это неизменяемый снимок категории продажи.
- core.offer_category_history: product_id + seller_id + valid_from; category_name (nullable), valid_to (nullable для текущей версии), provenance. Классификация относится к предложению конкретного продавца, а не автоматически ко всем продавцам одного product_id.
- Интервал [valid_from,valid_to), без пересечений для одной пары product_id/seller_id, valid_to > valid_from; не более одной открытой версии. Проверить ограничения на уровне базы (например, EXCLUDE по диапазону с btree_gist либо эквивалентный надёжный механизм).
- В одной транзакции закрыть старую версию и открыть новую; конкурентные изменения одного предложения сериализовать. Новая позиция получает категорию из версии, действующей при оформлении. Сохранённые категории старых позиций при смене справочника не обновлять.
- Текущий core.products.category_name можно оставить для совместимости как исходную/базовую классификацию. Источником исторической выручки должна стать категория позиции. Функцию/процедуру смены категории описать и использовать вместо произвольных UPDATE.

Исходные CSV не содержат прошлых изменений категорий. Начальную категорию старых позиций можно зафиксировать из текущего источника с provenance='source_baseline'; это НЕ доказательство фактической категории в прошлом. Даты прошлых смен не выдумывать. История изменений надёжно накапливается с момента внедрения. Повторная загрузка не должна перезаписывать снимки продаж текущей категорией.

Зависимости: queries/05_category_revenue.sql, queries/block_a_all.sql и mart.delivered_items должны брать категорию из снимка позиции, сохраняя NULL через LEFT JOIN. Последующие категорийные витрины наследуют это изменение. Остальные первые ответы не должны меняться.

## 2. Адрес на момент заказа

Предлагаемый интерфейс core.order_addresses:

- order_id: PK/FK к orders;
- zip_code_prefix text, city text, state text — снимок адреса оформления;
- captured_at + provenance, customer_unique_id при необходимости связи с человеком.

При первичной загрузке получить адрес через orders.customer_id → customers.customer_id. Новый заказ получает новый снимок. Обновление текущего профиля человека не меняет адрес уже оформленного заказа. Не соединять старые заказы с последним адресом по customer_unique_id.

В источнике есть только почтовый префикс, город и штат: улицу, дом и полный индекс не придумывать. Это адресная детализация, доступная в данных, а не полный почтовый адрес.

Зависимости: №7 и №9a должны читать state из core.order_addresses. То же для buyer_state в mart.order_metrics / mart.delivered_items и адреса в web/server/core.mjs. При отсутствии снимка заказ не терять: неизвестный регион + диагностика. Целевой инвариант — снимок на каждый заказ после загрузки.

## Приёмка миграции

1. Сохранить результаты всех десяти ответов до изменений.
2. На исходном наборе создать снимки; проверить равенство чисел, выручки и регионального распределения до/после.
3. На тестовых данных изменить категорию предложения: старые продажи остаются в старой категории, новые — в новой; другое предложение того же товара не затронуто.
4. Изменить адрес человека: старый заказ остаётся в прежнем штате, новый получает новый адрес.
5. Проверить повторную загрузку, конкурентную смену категории и отказ при пересечении версий; тесты изменения данных выполнять в отдельной базе/с откатом.
6. Прогнать checks/run_block_a.py --local-psql, checks/test_block_b.py, checks/run_block_b.py и тесты веб-приложения. Проверить backend-права на новые объекты отдельно.
